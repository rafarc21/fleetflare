# Weekly retro: learnings into checks/standards/prunes (board issue #165)

## The problem, as measured

Issue #165's own framing: "retro is not a memory system." The fleet already
has an ops-memory store (`apps/fleet/src/memory/store.ts`, `FLEET_OPS_REPO`-
backed, `fleet memory ls`/`compact`) and a structured per-task carrier for
learnings (`apps/fleet/src/board/envelope.ts`'s `learnings` field, flowing
through the teardown harvest at `src/studio/do.ts`'s `harvestLearnings`). What
is missing is the step AFTER accumulation: a periodic pass that reads what has
piled up — merged PRs, review findings, board envelopes, harvested memory —
and turns it into concrete environment changes (a new deterministic check, a
standards entry, a navigation pointer, a tool-economy fix, a bloat trim, or a
prune candidate). Without that pass, learnings sit in `fleet/memory/` or in
closed issue threads and never become a gate, a doc, or a removed stale check.

Issue #165 also names what this is NOT: a studio that reads learnings and then
quietly FILES the fix tasks itself. The retro proposes; the operator picks by
number; converting a picked number into a board task is the SAME `fleet task
new` every other task uses, run afterward, by whoever is running the retro
(maestro or the operator).

## The fix

Two deliverables, both read-only/proposal-shaped — neither one files or
mutates anything on its own.

### 1. `skills/retro-ritual/SKILL.md`

Modeled on `skills/sprint-ritual/SKILL.md`'s house voice (numbered decision
sheets, "do not filter decisions," recommended-option-plus-cost-of-being-wrong).
Covers:

- Purpose: retro turns learnings into environment changes; it is not itself
  a memory system (quoting issue #165's own framing).
- What it reads and where: last N merged PRs (`gh pr list --repo <owner/name>
  --state merged --limit N`), review findings (PR review comments / the
  `code-review` skill's own output on those PRs), board envelopes (`fleet task
  show <n>`, specifically each envelope's `learnings` field —
  `apps/fleet/src/board/envelope.ts`), and harvested ops memory (`fleet memory
  ls`, `apps/fleet/src/memory/store.ts` — empty when `FLEET_OPS_REPO` is unset,
  which the skill states explicitly rather than treating as a reason to
  refuse the retro).
- Six candidate categories, each with a one-line definition: new deterministic
  checks, standards entries, navigation pointers, tool-economy fixes, bloat,
  prunes (a check silent 30 days straight, or allowlisted more than N times —
  named as a removal CANDIDATE here, never removed by the retro itself).
- Output shape: a numbered decision sheet, same shape sprint-ritual's
  explorers already produce — each line names the candidate, a recommended
  action, the cost of getting it wrong, and a citation to the concrete
  PR/issue/session moment it traces to. No candidate ships without a citation.
- Explicit "proposes only" boundary, and that the weekly retro board task
  itself (not the fix tasks it proposes) is filed with `fleet task new
  --template retro`.

### 2. `fleet task new --template retro`

`apps/fleet/src/studio/cli-args.ts` already has a brief-flags grammar
(`TASK_FLAGS.new`, parsed through `parseFlags`) and a bare-boolean extraction
loop for `--junior`/`--provision`/`--fresh-session`. `--template` is a
VALUE-taking flag (`--template retro`), so it goes through the ordinary
`parseFlags` path — added to `TASK_FLAGS.new` — rather than joining the
bare-boolean loop, which only exists because those three flags take no value.

New pure module `apps/fleet/src/studio/retro-template.ts` exports
`RETRO_TASK_TEMPLATE: { title, objective, outputFormat, boundaries }` — the
same four fields `TaskBriefArgs` requires, written from the skill content
above. Design choices, so a future reader does not re-litigate them:

- **Title is static, not datestamped.** The GitHub issue number is the
  uniqueness key for every board task (same as every other `fleet task new`
  call) — a `new Date()` baked into this module would only make the retro
  task's title differ run to run, buying nothing, while turning this module's
  own parse tests non-deterministic for no real benefit. "Weekly" lives in the
  cadence the operator or maestro runs it at, not in the title string.
- **`--template` validates against a closed vocabulary of exactly one entry**
  (`"retro"`) in `parseTask`. An unknown value is a usage error naming the one
  valid value. This is deliberately NOT a registry/lookup-table design: with
  one template in existence, a registry buys nothing but indirection. Add one
  when a second template actually ships.
- **`--template retro` does not exclude the other brief flags.** An explicit
  `--title`/`--objective`/`--output`/`--boundaries` given alongside
  `--template retro` overrides just that one field; the rest still come from
  the template. This mirrors how `--sprint`/`--studio`/`--repo`/`--continues`/
  `--junior`/`--provision` already layer onto a brief — a template is a
  DEFAULT for the four required sections, not a separate mode.
- **Unassigned by default**, same as a plain `task new` with no `--studio` —
  cli-args.ts's own comment at the `TaskBriefArgs.assignee` doc already calls
  this "a real, intentional thing — files at a sprint meeting." A retro task
  is no different: the operator decides who runs it when they fan it out.

In `parseTask` (the `sub === "new"` branch), the four required-field checks
now read the template's own value as the fallback when the corresponding flag
was not given AND `--template retro` was. `VERBS["task-new"]` gains a mention
of `--template retro` in both `args` and `summary` so `fleet help`/`CLI_USAGE`
stay accurate by construction. No change to `cli/fleet.ts`'s `cmdTaskNew`: it
already forwards whatever `TaskBriefArgs` parsing produced, template-resolved
or not.

### 3. Blueprint wiring

`fleet/blueprint/studios/maestro/studio.md`: `retro-ritual` joins the
`skills:` frontmatter list, and one paragraph (placed near the other process
sections — Junior, Supervision) names the weekly cadence, points at the skill
for what the retro covers, and states that the weekly retro board task itself
is filed with `fleet task new --template retro`.
