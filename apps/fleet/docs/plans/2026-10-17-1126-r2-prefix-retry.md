# Plan: #1126 — R2-result prefix hides install/clone-failed from the retry rule

## Problem

`storedLegResult` (`apps/fleet/src/gate/leg-run.ts`) prefixes a leg result read
back from R2 with `result read from R2 after transport loss: `. `isRetryable`
matches `install failed` / `clone failed:` with `startsWith` on the description.
A container that stopped after writing `install failed` (or `clone failed:`)
therefore reads back as `result read from R2 after transport loss: install
failed ...` — the prefix hides the match, and the leg ends final after one
attempt instead of earning its one fresh-container retry. Regression from #1124.

## Fix

- Hoist the prefix literal into a shared exported constant `R2_PREFIX`.
- In `isRetryable`, strip `R2_PREFIX` when present before the `startsWith`
  checks, so a result recovered after transport loss matches on its underlying
  cause.
- Keep the presentational prefix everywhere else; no other behavior changes.

## Tests

- New test: an install-failed result read from R2 (state error) is retried once
  (dispatch count 2). RED first, then GREEN with the fix.
- Existing tests asserting the prefixed description stay green.
- `bun test test/bun/gate-leg-run.test.ts` and `bun run check` both pass.

## Blast radius

One predicate in the gate's leg runner. If wrong, a transport-loss-recovered
`install failed`/`clone failed:` still ends final after one attempt — the bug
this task fixes — or an unrelated description is wrongly retried. Confined to
the one-leg retry decision; no other consumer of `isRetryable`.
