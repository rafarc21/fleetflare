# Periodic WIP sync — bounding the loss window a platform container replacement opens (board issue #208)

## The problem

2026-10-03 ~05:33Z: a running studio's container was REPLACED (RST counter
+1, READY read "replaced — not brought up", a bare shell). No rescue-push
ran, and whatever was dirty or committed-but-unpushed in that container at
the moment of replacement was lost — recovered only via `fleet provision`.

The cause was not a fleet deploy: the last Worker deploy was 2026-10-02T13:48Z
and the image had been unchanged since 2026-10-01T21:10Z. So this was a
Cloudflare-side container replacement — a host move, an eviction, a platform
restart — not anything this codebase triggered.

That matters because every rescue path this fleet has today
(`rescuePushCmd`/`rescueSnapshotCmd`, `rescue.ts`) is a TEARDOWN-time rescue:
it runs because `fleet destroy`/`fleet park`/`fleet recycle` (or their
pre-restart/pre-recycle sync siblings) are ABOUT to kill the container and
get one last chance to save its work first. A platform-side replacement gives
this codebase no such chance — there is no pre-replacement hook to run
rescue AT. Teardown-time rescue, however correct, cannot close this gap by
construction: it is the wrong shape of fix for a kill this fleet never
initiated and never sees coming.

The fix accepted here is not to try to make teardown rescue fire anyway (it
structurally can't), but to add a PERIODIC safety net: push whatever is
dirty or unpushed to a dedicated ref every few minutes while the studio is
alive, so that whenever the next platform replacement lands — with no
warning, exactly like this one — the most it can cost is however much work
has piled up since the LAST periodic sync, not everything since the
studio's last real push. This bounds the loss window; it does not and
cannot close it to zero (only a successful teardown-time rescue can do
that, and this feature does not replace that one).

## This dispatch's scope (part 1 of 2)

Three pieces, all landed on `feat-208-wip-sync` (stacked on `main`, to be
rebased onto #212's branch later by someone else — see the board
reassignment note on issue #208):

1. **`wipSyncCmd` (`src/studio/rescue.ts`)** — a new, standalone command
   builder, closest in spirit to `rescueSnapshotCmd` (reuses its proven
   non-mutating snapshot technique: a throwaway `GIT_INDEX_FILE`, seeded
   from a byte copy of the real index, `commit-tree` against it rather than
   `git add -A`/`git commit` against the real index/HEAD) but otherwise its
   own function, not a variant of either existing builder:
   - **Fixed target, never generated**: `fleet/rescue/<studio>/wip`
     (`wipSyncRef`) — unlike every OTHER push target in this file, which
     always generates a fresh, timestamped, never-before-seen ref per call.
     One rolling snapshot per studio, overwritten every sync.
   - **Force-push, and ONLY here** — the one deliberate exception to this
     file's own repeated "never a `+`/`--force` push anywhere in this file"
     rule, documented in `wipSyncCmd`'s own doc comment at the point a
     future reader will actually see it. Safe specifically because the
     target is this ONE function's own exclusive, dedicated scratch ref —
     nothing else in the codebase ever writes to it or treats it as a real
     branch, so overwriting it can never clobber anyone else's work, only
     this same function's own prior snapshot.
   - **Main checkout only** — no worktree/branch/stash walk. A deliberate
     v1 scoping decision (see its own section below), not an oversight.
   - **Covers both shapes** `rescue_one`/`snapshot_target` already
     distinguish: a dirty tree (snapshotted and pushed by its synthetic
     SHA) and a clean tree that still holds commits no remote-tracking ref
     already has (`git rev-list --count HEAD --not --remotes`, pushed by
     `HEAD` — an existing commit, no snapshot needed). Nothing to sync at
     all emits `RESCUE_CLEAN`; a tree whose only change is a tool marker
     (#217) emits `RESCUE_MARKERS_ONLY` — neither attempts a push.
   - **No budget ledger, no retry** — `rescue_budget_ok`'s elaborate
     multi-push worst-case tracking exists because `rescuePushCmd`/
     `rescueSnapshotCmd` can run a first attempt plus an independent retry,
     several times, across a whole worktree/branch/stash walk. This
     function runs exactly ONE push, to ONE target, no retry (force already
     wins — there is nothing to retry against): a single `timeout`-bounded
     push is enough.
   - Emits the exact same output contract as the other two builders
     (`RESCUE_NO_CHECKOUT`/`RESCUE_CLEAN`/`RESCUE_MARKERS_ONLY`/
     `RESCUE_PUSHED <target> <count> <files|commits>`/`RESCUE_FAILED`), so
     `do.ts`'s existing `parseRescueExecResult` parses it with no changes
     beyond a new `label` value ("wip-sync") for its own error messages.

   TDD: `test/bun/rescue-push.test.ts` (existing file — it already carries
   the real-git fixture machinery, the `timeout`/`gtimeout`/perl-shim
   cross-platform handling, and the `checkout`/`origin`/`sh()`/`rescueRefs()`
   helpers every other suite in that file reuses) gained a new `#208`
   `describe` block, placed next to the existing `#266 — rescueSnapshotCmd`
   suite. RED confirmed first (`wipSyncCmd`/`wipSyncRef` did not exist yet —
   `bun test` failed with `SyntaxError: Export named 'wipSyncCmd' not found`),
   then GREEN after implementing. Coverage: a dirty main checkout force-pushes
   a snapshot to the fixed ref with real status/HEAD/origin's real branch
   untouched; a clean-but-ahead checkout force-pushes the existing HEAD
   commit the same way; a fully clean tree yields `RESCUE_CLEAN` with no ref
   ever created; a markers-only tree yields `RESCUE_MARKERS_ONLY`; no
   checkout yields `RESCUE_NO_CHECKOUT`; running it twice with two different,
   mutually non-ancestor dirty snapshots overwrites the SAME fixed ref
   (proving the push is a genuine force-push, not a silent fallback to a
   freshly generated one); a dirty member worktree is never rescued (proving
   the main-checkout-only scoping); and the generated command string carries
   exactly one `--force`. Full file: 141 pass, 0 fail.

2. **Wired into the existing 5-minute tick** (`syncSessionCycle`, `do.ts`) —
   no new scheduled loop. `STUDIO_TICKS`'s `syncSession` entry already runs
   every `SYNC_SESSION_SECONDS` (300s, `session-sync.ts`) — close enough to
   the issue's own "e.g. 10 min" that reusing this already-armed,
   already-budgeted (`TICK_DEADLINES_MS`), already heal-aware tick is far
   safer for a one-way-door feature than inventing a second schedule. The
   new step:
   - Sits right after `checkAndRecordReadiness`'s own call in the cycle, and
     is gated on that SAME call's verdict: `checked?.readiness?.kind ===
     "provisioned"`. A stopped studio, an unreachable one, or one this cycle
     simply couldn't confirm (`bare`/`inconclusive`) gets no WIP-sync exec at
     all — a narrower gate than the heal step immediately below (`if (heal
     && checked)`), which also fires on `bare` precisely so it CAN heal it;
     wip-sync additionally requires `provisioned` because, unlike heal, it
     execs commands into the container rather than restarting it.
   - Calls a new `wipSync(deps, repo, studio)` (`do.ts`), sibling to the
     existing `rescuePush`/`rescueSnapshot`: builds the command via
     `wipSyncCmd`, runs it via `deps.exec`, parses the result via the
     EXISTING `parseRescueExecResult` (now accepting a third `label` value,
     `"wip-sync"`, for its own error messages — no new parser).
   - On `RESCUE_PUSHED`: stamps `Observed.wipSyncedAt` (new field, below).
   - On `RESCUE_FAILED`, or any thrown error (including `wipSync`'s own
     `parseRescueExecResult` throw): `console.error`, loudly, and the cycle
     moves on — never blocks any other step in the SAME tick. This is the
     deliberate opposite of `rescuePush`/`rescueSnapshot`'s own posture
     (both explicitly throw, because their teardown callers must decide
     whether to refuse the kill): nothing here is being torn down, so a
     missed sync this cycle just means the next tick tries again.
   - On `RESCUE_CLEAN`/`RESCUE_MARKERS_ONLY`/`RESCUE_NO_CHECKOUT`: no stamp
     change — the previous `wipSyncedAt` (if any) is left exactly as it was,
     still valid evidence of the last REAL sync.

3. **New field**: `Observed.wipSyncedAt?: string | null` (`observed.ts`).
   Stamped (ISO "now") ONLY on an actual successful push
   (`recordWipSyncOnSuccess`, `do.ts`) — nowhere else. Follows the exact
   absence convention `restarts` already established on this same
   interface: OPTIONAL, deliberately left OUT of `emptyObserved()`, so a row
   that predates this feature (or a studio that has never had a WIP sync
   actually succeed) reads as truly ABSENT, never a fabricated `null`.
   Mechanically it rides `mergeObserved` the same way `lastSnapshotAt`
   already does — its own value on the existing `OBSERVED_KEY` blob, not a
   separate DO-storage key — because, unlike `restarts.ts`, there is no
   independent state machine behind this field that needs its own key.
   That means `do.ts`'s `getObservedWithActivity`/`withObserved` need NO
   code changes at all to carry it: `getObserved`'s own `{
   ...emptyObserved(), ...stored }` already passes any stored field through
   unchanged, so `wipSyncedAt` flows through those two functions for free,
   exactly the way `lastSnapshotAt` already does — read and confirmed before
   writing the field, not assumed.

## Why main-checkout-only (v1 scoping decision)

`rescuePushCmd`/`rescueSnapshotCmd` both walk every git worktree (the main
checkout plus every member subagent's own, under
`.claude/worktrees/<name>`), every local branch not checked out anywhere,
and every stash entry — because a ONE-SHOT teardown rescue has to be
exhaustive; there is no next chance. `wipSyncCmd` deliberately does not: it
runs on a 5-minute cadence as a BOUNDING safety net, not a one-shot rescue,
and the board issue's own Ask talks about "a running studio's container" and
"worktree dirty" in the singular. A member worktree's own uncommitted work
is still exposed to the SAME loss window this feature exists to bound for
the main checkout — that gap is real, and open for part 2 (or a later
follow-up) to close, not silently assumed away. Named here explicitly so a
future reader does not mistake the narrower scope for an oversight.

## Why force-push is safe here specifically

This file's own repeated rule — "never a `+`/`--force` push anywhere in
this file" — exists because every OTHER push target here is either a real
branch (a studio's own checked-out branch, or a local branch/stash the
walk discovers — force-pushing one of those could silently discard a
commit someone else pushed in the meantime) or a freshly generated,
never-before-seen ref (force is pointless there: a brand-new ref has no
existing tip to be rejected against, so a plain push always lands clean
anyway). `wipSyncCmd`'s own target, `fleet/rescue/<studio>/wip`, is neither
of those — it is this ONE function's own exclusive, dedicated scratch ref.
Nothing else in this codebase ever writes to it, reads it as a real branch,
or treats it as anything other than "the last periodic WIP snapshot", so
overwriting it every tick can only ever discard this same function's own
prior snapshot — which is exactly the intended behavior (a rolling safety
net, not a growing archive of one-off refs that would otherwise accumulate
for the whole lifetime of a long-lived studio).

## Why this reuses the existing 5-minute tick instead of a new container-side loop

`do.ts`'s `syncSessionCycle` already runs every `SYNC_SESSION_SECONDS` (300s)
per studio, already carries its own whole-tick deadline
(`TICK_DEADLINES_MS.syncSession`) and its own stopped/destroying-aware gate
(`runScheduledTick`'s `isStoppedIn`/`destroyingMarkerFresh` checks), and
already composes several independent, isolated, best-effort steps
(session-tar sync, aside-session ship, burn mirror, account failover,
readiness check, bare-container heal, deferred survival-brief retry,
detached install-cache save) behind individual `try`/`catch` blocks with no
step able to block another. Board issue #208's own Merge Danger note calls
this a one-way door (`container/` periodic job + rescue); adding a SECOND,
brand-new container-side scheduling mechanism for a periodic push — with
its own arm/disarm/deadline/stopped-studio logic to get right the first
time — would be strictly more blast radius than threading one more
already-isolated step into a schedule that has already been hardened,
tick after tick, against exactly the failure modes a new one would have to
rediscover (a studio that's `stopped`, a tick that runs long, a destroy
landing mid-tick, a step whose failure must never cost the others their
turn). Reusing the existing tick gets all of that for free.
