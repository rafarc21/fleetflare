# pin the heal-wake retry cap (board issue #178)

> Test-only follow-up from PR #170 (`1018064`, already merged to main).

## The gap, as measured

`retryPendingHealWake` (`apps/fleet/src/studio/failover.ts:1860-1891`) retries
a refused heal wake hourly (`AUTO_CONTINUE_RETRY_MS`), up to
`PENDING_HEAL_WAKE_MAX_ATTEMPTS = 3` (`failover.ts:1858`): on hitting the cap
it gives up silently — clears `pendingHealWakeAttempts`/
`pendingHealWakeLastTriedAt`, performs zero further exec. No existing test
ever drives the refusal past the cap. #170's own closest test,
`"a refused heal wake (transient pane-probe hiccup) gets a bounded retry on a
LATER tick, not lost forever"` (`test/studio.auto-continue.test.ts:425-460`),
stops at attempt #2 (one refusal, then one success) and never reaches
attempt #3 or the give-up branch at all. #178's own reported mutation result
confirms the hole directly: bumping `PENDING_HEAL_WAKE_MAX_ATTEMPTS` to `1e9`
left all 805 failover/wake tests green.

## Scope

IN: one new test in `test/studio.auto-continue.test.ts`, mirroring the
existing bounded-retry test's harness/fixture/refusal pattern, extended from
two ticks to five — forcing the refusal through three straight attempts
(reaching the cap) and then REMOVING the refusal on the tick that should be
capped-out, so the assertion that zero wake lands is actually load-bearing
(not vacuous — if the cap were disabled, that final tick would succeed).

OUT: no production code change. No change to `failover.ts`, `do.ts`,
`types.ts`, or `wake.ts`.

## Design

Same `harness()` (`studio.auto-continue.test.ts`), same `INLINE_PANE` →
`RECOVERED_IDLE` heal sequence, same `PANE_PROBE_CMD`-returns-`"...bash\n"`
refusal trick the existing bounded-retry test already uses to force
`runGatedWake` to refuse without touching #214's own heal evidence:

1. Degrade on `INLINE_PANE` (one account) → `exhausted`.
2. Heal tick (`RECOVERED_IDLE`, forced refusal): heals to `running`,
   `pendingHealWakeAttempts === 1`, zero `wakeCmd` execs.
3. Retry tick, 1h01m later (still forced refusal): `attempts === 2`.
4. Retry tick, 1h01m later (still forced refusal): `attempts === 3` — the cap.
5. Retry tick, 1h01m later, refusal REMOVED (exec restored to the harness's
   normal behavior — if the cap weren't enforced, this tick's retry would
   succeed and a `wakeCmd` would land): assert `pendingHealWakeAttempts`/
   `pendingHealWakeLastTriedAt` are cleared (`null`), and that `h.execs`
   contains zero `wakeCmd(AUTO_CONTINUE_PROMPT)` calls across the WHOLE test.

Step 5's inversion (dropping the refusal on the capped-out tick) is what
makes the final assertion a real mutant-killer: with the cap intact, nothing
ever attempts that 4th wake even though nothing is refusing it anymore; with
the cap disabled (or raised far enough), that same tick succeeds and the
assertion goes red.
