# Rescue-ref gaps left by #212's round-2 review

**Issue:** https://github.com/rafarc21/fleetflare/issues/216

**Goal:** PR #212 fixed "rescue pushes never land on the checked-out branch".
Its own round-2 review turned up six smaller gaps left behind — one real
silent-drop bug in the survival re-brief's rescue-ref plumbing, one real
shape-matching gap that makes three of rescue.ts's own ref shapes invisible to
the re-brief, two small correctness bugs in `rescue_one`'s generated bash, one
missing trailer, and one test gap. Six independent fixes, each pinned by its
own test.

## 1. MAJOR — `resolveSurvivalInput` only fetches rescue refs when a task is unresolved

`survival-delivery.ts`'s `resolveSurvivalInput` only calls
`sources.rescueBranches()` inside `if (unresolved.length > 0)`. A task whose
branch WAS resolved (via its own PR artifact, say) can still coexist with a
genuine rescue ref from a different, unrelated incarnation/crash of the same
studio — that ref is never fetched, never shown, the lead never told. A studio
with zero live tasks never fetches at all, same gap.

**Fix:** drop the `unresolved.length > 0` gate — always call
`sources.rescueBranches()`. `attributeRescueBranch`'s own single-candidate
logic is unchanged (still only attributes with exactly 1 unresolved task and
exactly 1 ref). When attribution does not happen, `unclaimedRescueBranches` is
every fetched+anchored ref the attempt did not assign — including the "0
unresolved tasks" case, which today sets it to `[]` unconditionally instead of
to the (possibly non-empty) fetched set.

**Test:** `test/studio.survival-delivery.test.ts` — one task whose branch
resolves via its PR artifact (so `unresolved.length === 0`) plus one real
anchored rescue ref on origin for this studio: `unclaimedRescueBranches` must
contain that ref. A second case covers the empty-task-list studio surfacing a
stray ref too.

## 2. MAJOR — `isRescueBranchFor` misses 3 ref shapes rescue.ts actually pushes

`isRescueBranchFor` only matches the flat `fleet/rescue/<studio>-<14digits>`
shape. `rescue.ts` has pushed three more shapes since #251/#263/#266, all
already anchored and matched by `discoverRescueRefsCmd` (provision.ts)'s own
grep pattern:

- `fleet/rescue/<studio>/wt/<id>-<14digits>` — a member worktree's own rescue.
- `fleet/rescue/<studio>/wt/<id>-nff-<14digits>` — that shape's own
  non-fast-forward retry.
- `fleet/rescue/<studio>/<14digits>/checkout/<branch-or-stash-name>` — N1/N2's
  own unpushed-local-branch/stash pushes from the main checkout's walk.

None of these ever matched the flat anchor (extra characters before the
digit run, or a `/` where the flat shape needs a trailing `-`), so a rescue
of any of these three shapes sat on origin, genuinely anchored and genuinely
real, completely invisible to the survival re-brief — the identical silent-
drop class #107 exists to fix, just for 3/4 of this file's own ref shapes.

**Fix:** extend `isRescueBranchFor` to also match the nested
`fleet/rescue/<studio>/` prefix, then the two sub-shapes under it
(`wt/<id>-<14digits>` optionally with `-nff-`, and `<14digits>/checkout/<name>`)
— same anchoring discipline as the flat case (a studio id cannot be a literal
prefix of a different studio id immediately followed by `/` or `-`, so no
escaping is needed), mirroring `discoverRescueRefsCmd`'s own pattern rather
than re-deriving a new one.

`do.ts`'s `survivalSources().rescueBranches` only queries GitHub's
matching-refs endpoint with the flat prefix. Fixed by querying the nested
prefix too (`listMatchingBranches` takes one prefix per call) and merging +
deduping. Extracted into a new exported, port-level, DO-free helper
(`fetchRescueBranchCandidates`, survival-delivery.ts) so this is testable
without constructing `StudioDO` (which cannot be constructed under
vitest-pool-workers — do.ts's own header).

**Test:** extends the existing `isRescueBranchFor`/`rescueBranchesFor` block
with the 3 new accepted shapes, re-confirms the existing rejected-garbage
cases still reject, and a new focused test on `fetchRescueBranchCandidates`
asserting it calls its injected `listByPrefix` exactly twice (the flat and
nested prefixes) and merges + dedupes the results.

## 3. MINOR — a dirty tree whose final content equals HEAD still gets "rescued"

`rescue_one`'s dirty-tree branch (`rescuePushCmd` and `rescueSnapshotCmd`,
mirrored) runs `git add -A` + `write-tree` into a detached index whenever
`git status --porcelain` shows anything. If a file was staged then reverted
back to its original bytes, the resulting tree is byte-identical to
`HEAD^{tree}` — but the code still commits and pushes it as a "rescue",
reporting `RESCUE_PUSHED ... success` for a push with nothing new in it.

**Fix:** right after `$tree` is computed (before `commit-tree`), compare it
to `git -C "$w" rev-parse "HEAD^{tree}"`. If equal, this dirty tree carries no
real change — fall through to the exact same bookkeeping the "clean tree"
branch below already does (ahead-of-origin check, `markers=1`, or nothing),
rather than committing and pushing an empty diff. Extracted that bookkeeping
into its own bash function (`rescue_check_ahead`) so both the genuinely-clean
path and this now-equivalent-to-clean path call the same code instead of two
copies drifting apart.

**Test:** `test/bun/rescue-push.test.ts` — stage a file, then revert its
content back to `HEAD`'s own bytes (porcelain still shows it dirty), confirm
rescue reports `RESCUE_CLEAN` (nothing pushed), and no new ref lands on the
fake origin. Mirrored for both `rescuePushCmd` and `rescueSnapshotCmd`.

## 4. MINOR — the shallow-clone fallback snapshot carries no `Rescued-From` trailer

`rescueTryPushFn`'s shallow-clone fallback (`rescue_try_push`, fired when a
push is rejected "shallow update not allowed" / "did not receive expected
object") builds a parentless snapshot commit with a single `-m`, unlike every
other rescue commit in this file (two `-m` flags: the message, then the
`Rescued-From: <branch>` trailer as its own paragraph).

**Fix:** thread `rbranch` through as a new, final positional argument —
`rescue_push` (which already threads `ref`/`src` positionally) gains an
optional 5th `rbranch` param, forwarded to `rescue_try_push`'s own new 5th
param, used as the fallback commit's second `-m`. `rescue_one`'s two call
sites into `rescue_push` (dirty-tree, now-shared-via-`rescue_check_ahead`
clean/ahead path) pass their own already-captured `$rbranch`. The two N1/N2
direct `rescue_try_push` call sites (branch walk, stash walk) are unchanged —
no 5th arg — and `rescue_try_push` defaults the param to the `ref` it is
pushing when the caller omits it, so an existing call site cannot regress.

**Test:** extends the existing issue #140 test (real pre-receive hook, real
disjoint-history private remote, forces the real fallback) to assert, via
`git log -1 --format=%B <pushed ref>`, that the body contains
`Rescued-From: main` (the checkout's real branch in that fixture).

## 5. NIT — `mktemp`'s 0-byte file breaks `GIT_INDEX_FILE` when no real index exists

`rescue_one` seeds its detached index from a *read* of the real one
(`cp "$realidx" "$idxfile"`) when it exists. `mktemp` itself already created
`$idxfile` as a real, empty (0-byte) file; when `$realidx` does not exist
that 0-byte file is left in place and handed to `GIT_INDEX_FILE`, which is
not a valid empty-index format — `add -A` then fails with
`RESCUE_FAILED ... add`, even though pointing `GIT_INDEX_FILE` at a
*non-existent* path would have made git create a fresh, valid, empty index
on its own.

**Fix:** `rm -f "$idxfile"` when `$realidx` does not exist, in both command
builders.

**Test:** skipped, with reasoning recorded here rather than forced. Every
real precondition that gets a worktree far enough to reach `rescue_one` — a
fresh clone, or a freshly-added `git worktree add` — already performs a
checkout, which always writes that worktree's own `.git/index` (or
`.git/worktrees/<id>/index`) as a side effect before `rescue_one` can ever
run. `rescue_one`'s own dirty-tree branch additionally requires `HEAD` to
already resolve to a real commit (`commit-tree -p HEAD`), which a
freshly-`git init`'d, never-checked-out repo does not have either. No
reachable fixture produces "a real worktree with a resolvable `HEAD` but no
index file" — forcing one (e.g. deleting `.git/index` by hand mid-test) would
pin a scenario this script can never actually hit, not a real gap. The code
fix is still applied defensively.

## 6. NIT — issue #49's second test doesn't confirm the real branch's own tip is untouched

`test/bun/rescue-push.test.ts`'s "#49" block has a test for a genuinely
unpushed commit on an upstream-less branch (`task/pr`) landing on a generated
`fleet/rescue/...` ref rather than the real branch. It checks the generated
ref exists and that `refs/heads/task/pr` is still *present* on origin, but
never captures `task/pr`'s own commit sha before/after the rescue run — a
regression that rewrote or moved that branch's tip would still pass today.

**Fix:** none needed in `rescue.ts` itself (this is a test-coverage gap, not
a production bug) — add the missing before/after sha capture.

**Test:** capture `git -C <origin> rev-parse refs/heads/task/pr` before
calling rescue and again after, assert they're equal — the same
before/after-sha idiom the neighboring "#49" test in the same `describe`
block already uses for its own `task/pr` assertion.
