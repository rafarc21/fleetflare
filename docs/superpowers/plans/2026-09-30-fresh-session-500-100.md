# `--fresh-session` silently dropped after a 500; retry resumes stale session (board issue #100)

## Field report

Operator, ~30-studio fleet, 2026-09-30 after 10:36Z rollout:
1. `fleet provision <id> --fresh-session` -> exec/bring-up failure mid-way
   ("degraded", HTTP-shaped error).
2. Retry `fleet provision <id>` (no flag) -> "resumed · snap 152m STALE".
   Fresh-session intent lost; old session restored.

## Root cause (confirmed by direct code reading, not a repro incident)

`cfg.freshSession` (`ProvisionConfig.freshSession`, `types.ts:352`) never had
a durable representation of its own. It lived ONLY as a local variable for
the ONE `runProvision` call carrying it
(`apps/fleet/src/studio/provision.ts`):

- `runProvision` (provision.ts:2447-2461) reads `cfg.freshSession` to (a)
  skip `adoptBeforeBringup` and (b) set `FLEET_FRESH_SESSION=1` on the ONE
  bring-up exec (`deps.sbExec(BRINGUP_CMD, ...)`, line ~2449).
- The bring-up exec throwing or returning non-zero (line 2452:
  `if (bringupRes.code !== 0) throw ...`) is caught by `runProvision`'s own
  OUTER try/catch (line 2357/2517) — every such failure funnels into ONE
  `"degraded"` status, returned NORMALLY (no re-throw). `freshSessionMoved`
  (provision.ts:2355) stays at its initial `false`: it is only ever set
  `true` AFTER the bring-up exec has already returned success (line 2461).
- `provisionWithStorage` (provision.ts, `if (freshSessionMoved) { ... }`,
  ~line 3580 pre-fix) only arms `SESSION_FORCE_KEY` — an UNRELATED
  next-sync-upload override (issue #37), not a "retry this fresh-session
  request" marker — and only on that same success path.
- Net effect: a failed `--fresh-session` bring-up left **nothing** durable
  anywhere recording that a fresh session had been requested.
  `cli-args.ts:88`'s own comment ("the Worker never persists it") is true by
  DESIGN for the happy path (a persisted role env must never silently
  replay `FLEET_FRESH_SESSION=1` into a later heal) — but it was ALSO,
  silently, true for the FAILED path, which the design never considered.
- The next plain `fleet provision <id>` (no flag) then took the ordinary
  `adoptBeforeBringup` branch (provision.ts:2447) and resumed whatever
  session state the container held — the exact "resumed · snap 152m STALE"
  symptom.

The 500 itself: `runSessionRestore`'s R2 read + bring-up's own restore/aside
steps are all individually guarded (own try/catch on the Worker side;
`(set +e ... ; true)` subshell in `container/studio-bringup.sh`'s
session-restore block) and can never abort the script. The
`FLEET_FRESH_SESSION` aside-move block itself (studio-bringup.sh:673-702)
guards each `mv`/`mkdir` with `if`, so a single failed move cannot kill the
script either. The exact trigger for a given 500 (network blip, an
exec-deadline kill on a slow aside-move over a very large session — the
"aside move ... on a big session" guess in the reassignment comment — or any
other transient exec failure) is NOT the bug: `runProvision`'s own design
already treats ANY such failure identically (one `"degraded"` catch-all,
provision.ts:2517). The BUG is that this catch-all silently erases the
fresh-session intent regardless of which underlying failure produced it —
so this fix does not chase one specific trigger; it closes the intent-drop
for all of them at once, matching the issue's own framing ("Also: find the
500 source" was secondary to "never silently resume a stale session").

## Fix chosen: (a) persist the intent durably before the risky work

The issue offered two acceptable shapes: (a) persist-and-retry, or (b)
refuse-until-re-passed. (a) was chosen because this codebase already has
the exact idiom for "an in-flight claim that must survive a throw" —
`OPERATION_KEY` (provision.ts:511, "written to storage BEFORE the work,
cleared in a finally") and `DESTROYING_KEY` (provision.ts:535) both follow
it. There is no precedent anywhere in this codebase for a provision verb
that refuses a bodyless retry, and (b) would be a new, unprecedented shape
for one narrow case. (a) is also the smaller diff: no new route/CLI surface,
no new error message contract for the operator to learn.

New key `FRESH_SESSION_PENDING_KEY` (`"freshSessionPending"`,
provision.ts, next to `OPERATION_STALE_MS`):

- `provisionWithStorage` reads it before calling `runProvision`. Effective
  freshness = `cfg.freshSession === true || pending === true`.
- If effective freshness is true, `FRESH_SESSION_PENDING_KEY` is armed
  (`put(..., true)`) BEFORE `runProvision` ever runs — durability-first,
  same ordering `OPERATION_KEY` uses.
- `runProvision` is called with `{ ...cfg, freshSession: true }` whenever
  effective freshness is true — so a bodyless retry still skips adopt and
  still sets `FLEET_FRESH_SESSION=1` on ITS OWN bring-up exec.
- Cleared (`put(..., false)`) ONLY when the attempt actually reaches
  `status.state === "running"`. Any other outcome (a clone failure, a
  bring-up throw, anything else `runProvision`'s catch-all turns into
  `"degraded"`) leaves it armed — deliberately conservative: an unrelated
  failure during a fresh-session-requested provision still keeps demanding
  freshness on the next attempt, which is strictly safer than the bug this
  closes.
- Not timestamped/stale-able like `OPERATION_KEY`: an unconsumed
  fresh-session request does not go stale on its own (unlike an in-flight
  lock, there is no concurrent-double-run hazard to age out).

No route/CLI change needed: `--fresh-session`'s existing behavior when it
DOES work is untouched; this only changes what happens after a failure.
