# pre-gate: fast cheap checks before a lead reports done (issue #105)

## Problem (verbatim gist, from #70 ask 1)

Full merge gate is serial, 10-20 min/train. ~40% of trains went RED on CHEAP
checks (a repo-invariants test, an icon-size lint test). A 30-second pre-gate
(invariants minus heavy build legs + one lint test + typecheck) caught every
one of them. Ask: a per-repo declared preflight command that a task report
runs BEFORE a studio may report done, result carried in the envelope.

## Investigation, with evidence (not guessed)

**Where does a studio's tmux pane find fleet.json?** `container/
studio-bringup.sh`'s own claude-launch step already answers this, byte for
byte: `repo_dir="/workspace/${STUDIO_ID%%--*}"` — the checkout claude itself
runs in. `STUDIO_ID` is injected into every studio's environment
unconditionally (`do.ts`'s `studioEnvVars`), never changes for the
container's whole lifetime, and is the SAME source claude's own cwd is
computed from. A lead's shell `cd`-ing mid-session does NOT move this —
`process.cwd()` inside `studio-fleet` would have been unreliable for exactly
that reason. Reused this derivation verbatim
(`resolveRepoRoot(env).STUDIO_ID.split("--")[0]` -> `/workspace/<repo>`)
rather than trusting cwd or inventing a second mechanism.

**Worker-side envelope validation** (`src/board/envelope.ts`'s
`parseEnvelope`): reads `raw` as a bag of KNOWN fields only (sender, intent,
status, artifacts, evidence, open_questions, context_digest, learnings,
verification, notes, task_id) and builds the stored `EnvelopeDoc` by hand,
field by field. An unknown key like `pre_gate` is neither validated NOR
stored NOR rendered — sending it costs nothing and buys nothing server-side
today. Decision: keep `pre_gate` CLIENT-SIDE / informational only for this
task. The refusal itself (client-side, before the POST is ever built) is
the actual enforcement the issue asks for ("RED pre-gate = not done"); a
Worker-side schema change to store/render `pre_gate` on the board is a
separate, larger piece (touches `envelope.ts`, `types.ts`,
`renderEnvelopeComment`) that this task's scope (container/ + blueprint.ts)
does not reach — noted here so it isn't silently assumed done.

## Design

**`FleetConfig.preflight?: string`** (`src/studio/blueprint.ts`). Same
"absent -> undefined no default, present-but-blank/wrong-type throws
BlueprintError naming the field" shape `Role.instance_type` already uses.
`parseFleetJson` validates + parses it.

**`container/studio-fleet` duplicates the same tiny parse** (own
`parseFleetPreflight`), per this file's own zero-relative-imports rule —
never imports `blueprint.ts`. New pure functions:
- `resolveRepoRoot(env)` -> `/workspace/<repo>` from `STUDIO_ID`, or null.
- `loadPreflightCommand(repoRoot)` -> reads `<repoRoot>/fleet.json`, reads
  `.preflight`, or null on ANY absence/malformed shape (missing fleet.json
  must never block `task report` itself).
- `runPreflight(cmd, cwd, timeoutMs = 30_000)` -> real `Bun.spawnSync(["sh",
  "-c", cmd], { timeout, killSignal: "SIGKILL" })`. A killed-by-timeout
  process (`exitCode` null) reads as exit 124 (shell "timed out"
  convention) — a FAILED gate, never a hang, never a silent pass. Output
  tail-truncated to 4000 chars.
- `evaluatePreGate(intent, status, preflight)` -> `{ refuse, reason? }`.
  `refuse` true ONLY when `preflight !== null && preflight.exit !== 0 &&
  intent === "result" && status === "ok"`. Every other combination (a
  "result" that is "blocked"/"partial"/"failed", or any non-"result"
  intent) still runs+attaches the gate but is NEVER refused — matches the
  issue's own framing ("lead runs it before posting THE DONE envelope"),
  not every report call.

**Wiring in `task report`'s branch**: when `loadPreflightCommand` returns
null (no fleet.json, or no `preflight` field), `finalBody` stays the raw
stdin `body`, byte for byte, UNPARSED — a complete no-op, zero behavior
change for every repo not opting in. Only when a preflight IS declared does
this script parse the envelope JSON (to read `intent`/`status` and to
attach `pre_gate`), run the gate, and either refuse (stderr + exit 1, no
request ever built) or attach `envelope.pre_gate = {cmd, exit, output}` and
post the augmented body.

## Deviations from the reassignment

- **git identity**: this container's `FLEET_BOT_NAME`/`FLEET_BOT_EMAIL` value
  is this operator's own private bot identity and matched the leak gate's
  own private denylist pattern #30 — the FIRST push was
  refused (`fleet: leak gate: text matches private denylist pattern`). Not
  this task's fix to make (that env var is only ever consumed by
  `container/server.ts`'s TASK-container git identity, which falls back to
  a public-safe `fleetflare[bot]` when unset — a STUDIO container like this
  one never programmatically sets git identity from it at all). Worked
  around it locally: `git config user.name/email` to the same public-safe
  `fleetflare[bot]` default, `--reset-author`'d the one already-local,
  never-pushed commit, then pushed clean. Flagging this as a real
  environment gap for the maestro: a fresh studio container with no git
  identity pre-configured will, if a lead reaches for `$FLEET_BOT_NAME`, hit
  this exact refusal.
- **junior**: tried first per instructions
  (`~/.claude/skills/junior/junior.sh --task "..." apps/fleet/container/
  studio-fleet`) — refused with "junior not authorized for your current
  task: only the maestro enables it, by filing the task with `fleet task new
  --junior`" (issue #105 carries no `junior` label). Did every investigation
  and drafting step myself, as instructed for the fallback case.
- **`bun test test/container.studio-fleet.test.ts`** (the reassignment's
  suggested targeted-test command) does not actually run that file — it is
  a `vitest`-only source-pin file (imports `cloudflare:test`), and
  `package.json`'s own `bun-test` script does not include it either. Used
  `bun run test -- test/container.studio-fleet.test.ts` (vitest) instead,
  which is the real, working equivalent.
- Worker-side envelope schema (`src/board/envelope.ts`) was NOT touched —
  see "Worker-side envelope validation" above for the evidence-based reason
  (`pre_gate` is client-side/informational only, per this task's own
  explicit "decide, using evidence" framing). If the operator wants
  `pre_gate` to actually land on the rendered board comment, that is
  follow-up work against `parseEnvelope`/`EnvelopeDoc`/
  `renderEnvelopeComment`, out of this task's container/+blueprint.ts scope.
