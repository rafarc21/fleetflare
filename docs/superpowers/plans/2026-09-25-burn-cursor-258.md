# Burn cursor: unbounded growth, silent under-counting, and a lost failure signal (board issue #258)

## Background

`src/studio/burn.ts`'s `BurnCursor` (#154's own offset/inheritance rule) is
the per-studio state `session-sync.ts`'s `syncSessionTick` diffs every tick's
session tar against, so token-burn counting never double-counts a line and
never re-parses a whole transcript from scratch. PR #173's own round-3 review
found five distinct problems in that design, none of them behavior bugs in
#154's core offset RULE itself — all in what surrounds it: the cursor's own
wire size, a length-only migration trust with no content check, unbounded
growth, a swallowed persist failure, and two now-inaccurate test names left
over from #154 superseding an even older mechanism. This plan covers all
five; two (encoding shrink, the N1 migration fix) landed first on
`fix-258-burn-cursor` at commit `41de0d4`, the remaining three (pruning
wiring, persist-failure visibility, stale test renames) land in this same
branch's follow-up commit.

## The five fixes

1. **Encoding shrink (landed, 41de0d4).** `BurnCursor.sessions` used to be
   keyed by the literal (project-prefix-stripped) session key string —
   70-90 realistic characters per subagent
   (`<uuid>/subagents/agent-<hex>`) — with each entry a `{counted, hash}`
   object. At 6,000 realistic subagent paths (a real observed fan-out
   shape) the persisted cursor exceeded the DO 2 MB value cap well before
   that count. Fix: `sessionMapKey()` renders each session key to a short,
   opaque structural id (two 32-bit rolls, no separator — never decoded
   back to the literal key, since every real caller already has the
   literal key fresh from `sessionKeyOf(member.file)`); each entry is
   compacted to a single wire string (`encodeSessionCursor`/
   `decodeSessionCursor`, `"<counted>:<hash-or-empty>"`). `resolveOffsets`
   also drops a per-path `fileHashes` entry whenever it is provably
   reconstructable from the session's own inheritance record at the exact
   same offset (recovered on the next read via rule (c)'s own fallback).
   Together this keeps 6,000 subagent paths under 1 MB (pinned in
   `test/studio.burn.test.ts`'s "6,000 realistic subagent paths" test) —
   comfortably inside the 2 MB cap, with margin over the issue's own
   "5,000 paths < 1 MB" target.

2. **N1: a divergent migration seed trusted on length alone (landed,
   41de0d4).** `legacySeed`'s migration-tick trust (pre-#154 cursor -> the
   new per-session inheritance map) used to check LENGTH only, with no
   content verification — a NEW same-session-key path whose bytes at the
   winning offset had genuinely DIVERGED from what that offset was
   actually counted against (a different conversation reusing an old
   offset number, not a continuation) was trusted anyway, under-counting
   (the review's own shorthand: "10 vs main 50"). Fix: `legacySeed` now
   also reports which PATH contributed the winning offset
   (`sourcePath`); `resolveOffsets` verifies that offset's fingerprint
   against `prev.fileHashes[sourcePath]` when one survives (i.e. the seed
   is a MIXED-version cursor — `fileOffsets`/`fileHashes` already real
   post-#154, only `sessions` unreadable under its new key for exactly one
   deploy tick), falling through to a full recount (the safe,
   over-counting direction) on a mismatch. A genuinely pre-#154 cursor
   (one with no `fileHashes` at all) has no fingerprint to verify
   against, so this check is a deliberate no-op there — that original
   migration shape keeps trusting length alone exactly as before this fix
   (pinned by its own guard test, since a hashless, pre-#154 cursor has no
   safer answer available at all).

3. **Pruning wired into the real tick (this commit).** `pruneCursor` and
   `CURSOR_PRUNE_MS` (48h — comfortably clear of
   `SESSION_SUBAGENT_WATERMARK_LOOKBACK_SECONDS`'s 24h worst-case budget-
   exclusion stretch) already existed as pure functions in `burn.ts`
   (pinned by their own `describe` block in `test/studio.burn.test.ts`),
   but nothing ever CALLED `pruneCursor` from `session-sync.ts`'s tick —
   without a caller, a burn cursor entry was never dropped once written at
   all (measured: 1.77 MB at 5,000 paths, the 2 MB cap reached near
   ~5,900), the exact unbounded-growth failure pruning exists to prevent.
   Fix: `parseUsageIncrement`/`burnIncrement` now both also report
   `presentPaths` — every jsonl member actually seen THIS tick, regardless
   of whether `resolveOffsets` found anything NEW to count for it (needed
   because pruning has to distinguish "seen just now" from "stale
   `lastSeenAt` left over from before this tick's own update"); the
   streaming `burnIncrement` derives it for free from pass 1's own
   deduped member list, so the two engines can never disagree on it (both
   already parity-tested against each other, `test/bun/session-memory.
   test.ts`'s `bothEngines`-style comparisons). `session-sync.ts`'s
   `parseBurn` now prunes the resolved cursor against `presentPaths`
   before the atomic `BURN_CURSOR_KEY`+`BURN_KEY` put.

4. **A failed cursor/burn persist was indistinguishable from an ordinary
   parse failure (this commit).** `parseBurn`'s own try/catch already
   existed for burn's advisory-only contract (a throwing
   `burnIncrement`/`parseUsageIncrement` must never fail an
   already-successful sync tick) — but that SAME catch also silently
   swallowed a `storage.put` REJECTING (a genuine DO storage error, e.g.
   "value too large"), logging the same generic "burn parsing failed"
   line for both. That conflates two very different failures: a parse
   failure means burn never computed anything for this tick, but a put
   failure means it computed a CORRECT delta and then LOST it — the next
   tick's `prevCursor`/`prevBurn` reads land right back on the same stale
   values, with no signal anywhere that anything went wrong. Fix: the
   `storage.put({[BURN_CURSOR_KEY]:..., [BURN_KEY]:...})` call now has its
   own inner try/catch with a distinct, greppable log message ("burn
   cursor/burn PERSIST FAILED"), and records the failure on
   `SESSION_GUARD_KEY` — the one status-mirroring channel
   `session-sync.ts` already owns that `do.ts`'s `mirrorBurnToRegistry`
   already mirrors onto `StudioStatus.sessionGuard` every tick, with no
   new channel invented. The burn watermark still does not advance over
   such a tick (same contract as any other burn failure), and the alert
   check never runs against a delta that was never actually made durable.

5. **Two stale test names in `test/bun/session-memory.test.ts` (this
   commit).** Both predate #154's `resolveOffsets` rules and had been
   silently superseded without ever being renamed:
   - `"shrink belt: stored offset past the file's end resets to 0"` —
     its fixture path matches `SESSION_PATH_RE` (has session identity), so
     it no longer exercises the pre-#154 no-identity shrink belt at all;
     empirically it now exercises rule (f) (a legacy-seeded offset far
     past the file's current length holds at its own end, not a reset to
     0). Renamed to `"#154 rule (f): a legacy-seeded offset far past the
     file's current end holds there, no reset to 0"`.
   - `"#130: a same-named file with DIFFERENT content inherits nothing"`
     — #130's own basename-matched sibling inherit is gone (subsumed by
     #154's session-key rule); empirically this fixture (a genuinely
     pre-#154 cursor, no `fileHashes`) exercises the OPPOSITE of its own
     name: a same-key sibling is inherited by LENGTH ALONE despite
     genuinely diverged content, exactly the trust the N1 fix above
     deliberately leaves unchanged for a cursor with no fingerprint to
     verify against. Renamed to `"pre-#154 cursor (no fileHashes): a
     same-key sibling is trusted on LENGTH alone despite genuinely
     diverged content"`. Neither test's behavior or assertions changed —
     both still only assert `burnIncrement`/`parseUsageIncrement` parity,
     never a specific counted value.

## Test strategy

RED-then-GREEN for every fix that changes behavior (3 and 4); 5 is a pure
rename (assertions unchanged, verified still green); 1 and 2 were already
RED-then-GREEN on `41de0d4` and are reconfirmed green here, not redone.

- `test/studio.burn.test.ts`:
  - "parseUsageIncrement/burnIncrement report presentPaths (issue #258
    pruning wiring)" — the pure-function half of fix 3: every present
    member reported regardless of new content, an absent-from-this-tick
    path never reported, `burnIncrement` and `parseUsageIncrement` agree.
  - "syncSessionTick — burn cursor pruning is wired into the real tick
    (issue #258)" — the integration half: a path absent from the tar for
    >= `CURSOR_PRUNE_MS` is pruned from the NEXT tick's persisted cursor;
    a path absent for under the threshold is retained. Both run
    `syncSessionTick` over a real gzip'd tar via a generalized fixture
    (`fakeSyncDepsWithFiles`, an arbitrary path-set variant of the
    existing single-file `fakeSyncDepsWithJsonl`).
  - "syncSessionTick — a failed burn cursor/burn persist is visible, not
    silently swallowed (issue #258)" — fix 4: a `storage.put` that rejects
    the cursor+burn pair logs the distinct message, records it on
    `SESSION_GUARD_KEY`, leaves `BURN_KEY` unwritten, and the watermark
    does not advance — while the sync tick's own result still reports the
    session tar shipped successfully (burn stays advisory-only).
- `test/bun/session-memory.test.ts` — the two renamed cases (fix 5), run
  unmodified in behavior; full-file bun-test run confirms no regression
  (same 10 pass / 0 fail / 18 `expect()` calls as before the rename).

## Files touched

- `apps/fleet/src/studio/burn.ts` — `presentPaths` added to
  `parseUsageIncrement`'s and `burnIncrement`'s return shape (fix 3 only;
  `pruneCursor`/`CURSOR_PRUNE_MS`/the encoding-shrink/N1 machinery already
  landed on `41de0d4`).
- `apps/fleet/src/studio/session-sync.ts` — `parseBurn` now prunes the
  cursor against `presentPaths` before persisting (fix 3), and wraps the
  cursor/burn `storage.put` in its own try/catch with a distinct log
  message and a `SESSION_GUARD_KEY` write on failure (fix 4).
- `apps/fleet/test/studio.burn.test.ts` — new `presentPaths` pure-function
  tests, new pruning-wiring integration tests, new persist-failure
  visibility test (fixes 3 and 4).
- `apps/fleet/test/bun/session-memory.test.ts` — two test names corrected
  to describe what they actually exercise post-#154 (fix 5); no behavior
  change.
